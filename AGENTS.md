# Работа над GRoute

GRoute — клиент на основе HyRoute. Рабочий каталог владельца — `C:\Projects\GRoute`, удалённый репозиторий — `git@github.com:benny52/GRoute.git`. Общаемся по-русски. Термины интерфейса согласуем с владельцем.

## С чего начинать

Прочитай `docs/PROJECT_SPEC.md`, затем относящиеся к задаче разделы `docs/ARCHITECTURE.md` и `docs/GUIDE.md`. `CLAUDE.md` из исходного проекта помогает разобраться в архитектуре и проверках. Порядок работы с Git задают договорённости владельца и этот файл. При расхождении поведения кода и руководства проверь путь от интерфейса до сохранения настроек и запуска движка.

Проверь корень Git, текущую ветку, состояние рабочей копии и адрес origin. Если проект пока скопирован без истории Git, открыт main или рабочая ветка не определена, чтение можно продолжить. Перед изменением программы согласуй, в какой существующей рабочей ветке вести разработку. Main предназначена для готовых версий. Публикацию, push, PR, слияние и релиз выполняй по явной команде. Сохраняй изменения владельца. Соблюдай лицензию и уведомления исходного проекта при распространении.

## OpenSpec и Superpowers

OpenSpec ведёт согласованные изменения поведения: предложение, затрагиваемые возможности, сценарии приёмки и задачи. Сначала проверь наличие `openspec/`, CLI и его версии. При первом подключении используй официальный OpenSpec с интеграцией Codex и синтаксисом установленной версии. Если нужна загрузка, сообщи, что именно потребуется. На этапе подготовки документов достаточно описать порядок; установку выполни на этапе, согласованном с владельцем.

Для сложной задачи используй подходящие навыки Superpowers: разбор требований для неоднозначного поведения, диагностику для воспроизводимого сбоя, план для сквозного изменения, проверку результата перед завершением. Для небольшой понятной правки достаточно обычного рабочего процесса. Один навык читай из одной установки. Храни план работ в задачах соответствующего изменения OpenSpec. Отдельный дублирующий план не требуется. Проверяй предложение командой валидации установленной версии; результат такой проверки относится к спецификации.

## Реализация и проверки

Первая поставка GRoute — портативный Windows-клиент (ZIP с `GRoute.exe`). Задачи установщика относятся к следующему этапу. У исходного клиента запуск EXE из распакованного каталога всё равно открывает данные HyRoute в AppData. Для пробы Windows-клиента сначала проверь изоляцию каталогов настроек и WebView2.

### Технические договорённости из CLAUDE.md

- Клиент использует Go, Wails v2 и Svelte 5. В Windows трафик перехватывает WinDivert, защиту при разрыве обеспечивает WFP. Для изменений маршрута проверяй и выбор действия в правиле, и обработку нового соединения движком.
- Для изменённого Go-кода проверь `gofmt`, затронутые пакеты через `go vet` и `go test`. Для изменений конкурентного доступа добавь проверку с `-race` в поддерживаемой среде. Каталог `third_party/` исключи из массового форматирования.
- Для изменённого Svelte-интерфейса проверь типы через локальный `svelte-check --threshold warning` и сборку Vite. В сборку Windows встраивается `frontend/dist`, поэтому при подготовке поставки обнови его из тех же исходников. Изменения для пользователя опиши в `docs/GUIDE.md`, при подготовке версии — в её примечаниях к выпуску.
- Маскируй данные аутентификации и пароли обфускации в журналах. Статистика хранит сведения о программах, серверах и группах. Домены посещённых сайтов на диск в статистику не записываются. Порядок сообщения об уязвимости описан в `SECURITY.md`.

### Договорённости владельца

- До реализации покажи подход и получи согласие. Уже согласованные шаги выполняй самостоятельно. Существенные изменения границ согласуй отдельно.
- Профили серверов сопоставляй по устойчивым идентификаторам. Учитывай активные и сохранённые профили правил, основной маршрут, порядок резервов и уже работающие старые конфигурации. Для затрагиваемых форматов сначала используй существующие модели Go и Svelte.
- Для маршрутизации, импорта и массовых операций воспроизводи проблему на искусственных данных. Проверяй обычный путь пользователя и повторное открытие сохранённых настроек. Для интерфейса выполни короткую проверку взаимодействия. В отчёте различай чтение кода, тест парсера, тест интерфейса и реальное соединение.
- Для теста сборки используй отдельный каталог данных. Доступы к VPN, приватные ключи, URL подписок, рабочие файлы настроек и дампы не включай в коммиты, отчёты или тестовые примеры. Изменения рабочей установки, настроек Windows, служб, драйверов, антивируса и VPN требуют отдельной команды владельца.
- Перед первой тяжёлой сборкой оцени загрузки и место с учётом имеющихся кешей. Скачивай только нужные для согласованного этапа компоненты. Храни временные файлы в исключённой из Git `.work/`. Завершай собственные тестовые процессы. В финале укажи, что изменено и что удалось проверить.

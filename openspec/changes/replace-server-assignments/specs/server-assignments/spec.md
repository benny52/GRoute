## Purpose

Пользователь может проверить все назначения сервера, заменить их в выбранной области и сохранить различие между конкретным сервером и выбором на главной.

## ADDED Requirements

### Requirement: Изменение нескольких цепочек в одном окне

GRoute SHALL показывать предлагаемые приоритетные и запасные серверы в строках правил сразу при редактировании и сохранять изменённые строки вместе.

#### Scenario: Разные назначения и отмена
- **WHEN** в общем редакторе пользователь назначает YouTube цепочку A → C, а Telegram цепочку B → C
- **THEN** обе цепочки видны до сохранения, отмена сохраняет старые назначения, а «Сохранить» записывает обе цепочки одной операцией

#### Scenario: Копирование в мастере
- **WHEN** пользователь распространяет цепочку одного VPN-раздела на все VPN-разделы и меняет приоритетный сервер только у Telegram
- **THEN** порядок запасных сохраняется, а итог мастера показывает индивидуальный приоритетный сервер Telegram

#### Scenario: Удаление отдельного сервера с главной
- **WHEN** пользователь удаляет выбранный на главной сервер A, который является приоритетным у YouTube и вторым запасным у Telegram в другом профиле
- **THEN** до подтверждения видны затронутые правила, после «Всё равно удалить» у YouTube приоритет «Основной сервер», у Telegram удалён только A из запасных, а на главной можно выбрать новый сервер


### Requirement: Область и роль замены

Клиент должен (SHALL) изменять только назначения в явно выбранной области и роли. Конкретный сервер определяется по ID. Порядок правил и относительный порядок сохранённых запасных серверов сохраняются.

#### Scenario: Установка приоритетного сервера у правил с разными назначениями
- **WHEN** в «Работе» у YouTube приоритетным выбран server1, у Telegram — server2, у обоих запасной сервер server3 и пользователь открывает «Групповое изменение» → «Приоритетный сервер», выбирает server4 и отмечает обе строки
- **THEN** предпросмотр показывает обе замены без выбора старого сервера. После применения и перезапуска приоритетный сервер обоих правил — server4, запасной — server3. «Локальная сеть» с действием DIRECT и правила BLOCK недоступны для выбора. Неотмеченные строки не меняются.

#### Scenario: Назначение запасных серверов галочками
- **WHEN** в «Групповом изменении» пользователь выбирает «Запасной сервер», задаёт server5 → server4 и отмечает только YouTube
- **THEN** видит старую и новую цепочки. Отмена оставляет исходную цепочку. После применения и перезапуска у YouTube именно два запасных сервера в указанном порядке и прежний приоритетный сервер, у Telegram оба поля прежние. Пустой новый список с подтверждением очищает только отмеченные запасные серверы.

#### Scenario: Адресная замена во всех профилях
- **WHEN** server1 — приоритетный сервер у YouTube в «Работе» и второй запасной сервер в цепочке B → server1 → C в неактивном профиле «Дом»
- **THEN** в текущем профиле видно только YouTube. При явном выборе всех профилей и обеих ролей предпросмотр показывает два изменения, включая «Дом, запасной № 2». После замены на D итог в «Доме» — B → D → C без активации «Дома». Выбор отдельной роли изменяет только соответствующую строку.

#### Scenario: Повтор и приоритетный сервер среди запасных
- **WHEN** закреплённый A заменяют на уже присутствующий закреплённый B в списке запасных серверов A → C → B → D или новый приоритетный сервер B уже есть среди запасных серверов
- **THEN** в первом случае предпросмотр запасных серверов показывает B → C → D, во втором совпадающий с приоритетным запасной сервер удалён. DIRECT и BLOCK сохраняют свои действия. Повтор уже применённой замены показывает ноль изменений.

#### Scenario: Выключенное правило и маршрут по умолчанию
- **WHEN** выключенное VPN-правило и VPN-маршрут «Всё остальное» содержат A, а замена охватывает их профиль
- **THEN** оба изменения показаны с разными подписями. «Всё остальное» подсчитано отдельно от правил. После применения выключенное правило остаётся выключенным. При выборе только строки правила маршрут по умолчанию сохраняет своё назначение.

### Requirement: Динамический выбор на главной

Клиент должен (SHALL) предлагать в поле «Приоритетный сервер» значение «Основной сервер» с пояснением о выборе на главной в редакторе, мастере и массовой замене. Этот пункт всегда первый, а текущее значение с главной показывается рядом. Ссылка на главный сервер или группу сохраняется отдельно от явного выбора того же ID.

#### Scenario: Порядок списка и независимость выбора на главной
- **WHEN** пользователь открывает список «Приоритетный сервер» в редакторе, мастере или групповом изменении при доступных Vless-Ger и Xhttp-swe
- **THEN** первым всегда показан «Основной сервер», в том числе при пустом выборе на главной. Далее доступны конкретные Vless-Ger и Xhttp-swe. Если на главной выбран Vless-Ger, выбор «Vless-Ger» по имени закрепляет его ID за правилом. После выбора Xhttp-swe на главной новые соединения наследующего правила используют Xhttp-swe, а закреплённого — Vless-Ger при его доступности. После сохранения и повторного открытия каждого правила способ выбора сохраняется. Ни одно из трёх окон назначения не меняет глобальный выбор.

#### Scenario: Старые правила и повторное открытие мастера
- **WHEN** в старой конфигурации одно правило наследует B, второе явно закреплено за B и пользователь добавляет через мастер правило с иным способом выбора, но теми же условиями
- **THEN** предпросмотр и сохранение различают назначения. После перезапуска и переключения главного B → D новое соединение по наследующему правилу выбирает D, по закреплённому — B при доступном B. В мастере выбор по имени и наследование доступны и при одном сервере.

#### Scenario: Закреплённый запасной сервер временно совпал с главным
- **WHEN** у наследующего правила явные запасные серверы C → D, пользователь выбирает C главным, повторно сохраняет правила и затем выбирает B главным
- **THEN** при главном C эффективная цепочка содержит C один раз. После выбора B явные запасные серверы снова C → D. Замена конкретного B сохраняет наследование. При выборе самого наследования источником пользователь может массово закрепить сервер.

#### Scenario: Удаление последних явных назначений
- **WHEN** пользователь переводит выбранные VPN-правила на наследование и убирает все их явные запасные серверы
- **THEN** до подтверждения видно сообщение «Эти правила будут использовать основной сервер с главной. После добавления других серверов назначения можно поменять массово». При отмене сохраняются старые назначения. При применении сохраняются сами правила и их порядок.

#### Scenario: Нет ни одного сервера
- **WHEN** для наследующего VPN-правила отсутствуют серверы
- **THEN** интерфейс показывает «Ожидает основной сервер». При действующей обработке трафика попытка нового соединения по VPN-правилу отклоняется без прямого выхода. После добавления и выбора основного сервера правило использует его без редактирования. Проверка включает решение движка и отсутствие вызова прямого выхода.

### Requirement: Использование сервера и удаление ручной копии

Клиент должен (SHALL) показывать ссылки на сервер по профилям, правилам, ролям и номерам запасных серверов. Для ручной копии сервера из подписки доступно действие «Перенести назначения и удалить копию».

#### Scenario: Карточка и полный перенос
- **WHEN** A и A′ имеют одно имя, разные ID и одинаковые параметры подключения, A выбран главным, используется вторым запасным сервером в одном профиле, приоритетным в другом, а также в группе и локальном прокси
- **THEN** карточка и предпросмотр называют оба профиля и правила, роль и номер запасного сервера, группу, прокси и главный выбор. Наследующие правила помечены как косвенное использование. При подтверждении все явные ссылки и главный выбор переходят на A′, а наследующие правила сохраняют наследование. После повторного открытия остаётся один сервер из подписки, оба профиля правил сохранены.

#### Scenario: Совпали только имя или адрес
- **WHEN** имя или адрес совпадает, а параметры транспорта, авторизации или защиты различаются
- **THEN** клиент различает серверы и не предлагает удаление как равнозначной копии. Просмотр и сообщения не раскрывают секреты подключения.

### Requirement: Удаление общей подписки
Клиент должен (SHALL) после одного подтверждения удаления подписки перевести затронутые приоритетные назначения VPN-правил на «Основной сервер» и убрать ссылки на её серверы из запасных серверов во всех профилях правил.

#### Scenario: Удаление SUB1 и последующее подключение другого сервера
- **WHEN** в профиле «Работа» настроены три правила из примера предложения, SUB1 — единственная подписка, других серверов нет, а на главной выбран server1
- **THEN** до удаления показаны YouTube и Telegram, их прежние приоритетные серверы, общий удаляемый запасной сервер и опустевший основной сервер. Отмена сохраняет SUB1 и назначения. После подтверждения SUB1 и её три сервера удалены, оба правила наследуют основной, список запасных серверов пуст. Локальная сеть идёт напрямую. После перезапуска и выбора нового основного оба VPN-правила используют его без редактирования.

#### Scenario: Удаление только части цепочки
- **WHEN** в другом профиле приоритетный сервер и запасные серверы B и C принадлежат другой подписке, между B и C стоит server3 из SUB1, а на главной выбран B
- **THEN** при удалении SUB1 одно подтверждение охватывает оба профиля. В другом профиле исчезает только server3, остаются прежний приоритетный сервер и запасные серверы B → C. Главный выбор B сохраняется. Выключенные VPN-правила и маршрут «Всё остальное» проверяются наравне с остальными.

#### Scenario: Весь трафик и исключения
- **WHEN** выбран режим «Весь трафик», маршрут «Всё остальное» наследует основной, YouTube явно использует другой доступный сервер и локальная сеть идёт напрямую
- **THEN** после смены основного новые соединения без совпавшего правила идут через выбранный на главной сервер, YouTube использует закреплённый приоритетный сервер, локальная сеть остаётся прямой.

### Requirement: Подсказка о трёх ролях в мастере

Мастер должен (SHALL) в шаге серверов рядом с выбором «Приоритетный сервер» объяснять основной, приоритетный и запасной серверы в существующем стиле пояснений.

#### Scenario: Пояснение до выбора и проверка итога
- **WHEN** пользователь настраивает в мастере два VPN-пункта при основном Vless-Ger, в одном оставляет «Основной сервер», в другом явно выбирает Vless-Ger и указывает запасной Xhttp-swe
- **THEN** до выбора видно, где меняется основной, когда приоритетный остаётся закреплённым и почему запасной подключается заранее. На итоговом шаге различимы наследующее и явное назначения, у второго показан запасной. При смене основного после сохранения только наследующее назначение следует за ним.

### Requirement: Причины запуска работающих серверов

Главная страница должна (SHALL) показывать для каждого туннеля его фактическое состояние и причины, по которым он нужен действующей конфигурации.

#### Scenario: Подсчёт по ролям
- **WHEN** у Vless-Ger есть три явных приоритетных назначения, а у Xhttp-swe пять запасных во включённых VPN-правилах активного профиля
- **THEN** строки этих серверов показывают «Приоритетный сервер в 3 правилах» и «Запасной сервер в 5 правилах». Выключенные правила, DIRECT, BLOCK и неактивные профили не увеличивают числа. Повтор в одной роли одного правила учитывается один раз. При наличии у сервера обеих ролей показаны оба числа.

#### Scenario: Смена основного и другие причины
- **WHEN** кроме явных назначений два правила наследуют основной сервер, пользователь меняет основной, а отдельный туннель нужен только активному локальному прокси или группе
- **THEN** после обновления статуса «Основной сервер для 2 правил» отображается у нового основного, явные роли сохраняют свой счёт. Строка «Всё остальное», используемая группа и востребованный прокси указываются как отдельные причины, когда участвуют в запуске. Серверу при подключении, ожидании или ошибке показывается фактическое состояние. Готовому запасному не приписывается передача трафика только из-за назначения.

### Requirement: Целостность переноса

Клиент должен (SHALL) применять подтверждённый результат целиком с учётом изменений между просмотром и записью. Частичный перенос не может стать действующей конфигурацией.

#### Scenario: Устаревший предпросмотр
- **WHEN** после просмотра изменилось затрагиваемое правило, состав группы, главный выбор или пара серверов
- **THEN** применение требует обновить предпросмотр до записи. Отмена и повтор исходного запроса сохраняют посторонние настройки.

#### Scenario: Неизвестные ссылки, сбой записи или прерывание
- **WHEN** часть ссылок недоступна для проверки, возникает ошибка между записями файлов либо процесс прерывается до завершения переноса
- **THEN** при неизвестных ссылках удаление останавливается с указанием причины. При сбое восстанавливается исходный комплект, включая подписку и её серверы при удалении SUB1 или оба экземпляра при переносе копии. После прерывания до возобновления маршрутизации доступно целое исходное либо целое подтверждённое состояние. Проверка охватывает также неактивный профиль, группы, прокси и главный выбор.

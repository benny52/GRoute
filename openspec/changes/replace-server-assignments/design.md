## Goals / Non-Goals

Первое изменение охватывает пункты 1 и 7. Формат первой поставки — portable ZIP для Windows. Для испытаний нужен отдельный каталог данных. Исходный `store.DefaultDir` ведёт в AppData HyRoute даже при запуске из ZIP. Размещение пользовательских данных и источник обновлений portable-сборки следует определить до её первого пользовательского запуска и выпуска соответственно. Сборка, установщик и внедрение обработки дублей при импорте не входят в этот этап.

## Decisions

1. **Один расчёт на стороне Go.** По идентификаторам профиля правил, правила и сервера строить список изменений с порядковыми номерами запасных серверов. Активный снимок считать один раз, сохранённый профиль читать без переключения. Вариант с серией вызовов сохранения из Svelte потребовал бы переключать контекст и оставлял бы уже записанные профили при последующей ошибке.
2. **Два смысла выбора.** Конкретный сервер или группа хранят свой ID. Выбор «Основной сервер» в поле «Приоритетный сервер» использует существующее пустое значение. При смене главного пересчитывается эффективный маршрут для новых соединений. Прежние конфигурации читаются в прежней семантике, без массовой перезаписи при открытии. Это относится и к существующим пустым ссылкам в запасных серверах.
3. **Групповое изменение.** Основной путь — задать приоритетный сервер или упорядоченные запасные серверы сразу списку отмеченных правил, независимо от их прежних значений. Роль и новое значение выбирают до отметки строк. Адресная замена по старому ID остаётся дополнительной командой. В выбранных строках менять только отмеченные правила. Для области целого профиля учитывать VPN-строку «Всё остальное», в предпросмотре считать её отдельно. Замена конкретного ID затрагивает явные ссылки, включая выключенные VPN-правила. Наследование можно выбрать отдельно источником или результатом. Для снятия назначений явно предлагать выбор «Основной сервер» в поле «Приоритетный сервер» и очистку выбранных запасных серверов. При замене убрать постоянные повторы, сохранив первое вхождение. Временное совпадение закреплённого запасного сервера с унаследованным главным движок пропускает, сохраняя закрепление при следующей смене главного.
4. **Перенос с удалением.** Перечислить всех потребителей старого ID, включая основной выбор (в том числе сохранённый активный сервер при основной группе), группы и локальные прокси. Если перенос известной ссылки меняет порядок или устраняет дубль, показать итог. Если назначение нельзя безопасно прочитать или перенести, объяснить препятствие и сохранить копию. Перед подтверждением не писать файлы и не активировать профиль.
5. **Удаление подписки.** Взять все ID, принадлежащие SUB1, обработать явные приоритетные назначения, каждую позицию запасных серверов и выбор на главной. Правило с удалённым приоритетным сервером переходит на «Основной сервер», удалённые запасные серверы исключаются. Если удалён выбранный основной, показать пустой выбор, исключить неявную подстановку другого ID при записи или чтении. Проверить поведение при сохранённой основной группе. Подписку, серверы, правила и выбор на главной сохранять согласованно. Группы и независимые локальные прокси показывать отдельно: предлагаем сохранить как ручные только серверы, необходимые этим потребителям, и назвать их до удаления. Явная ссылка правила сама по себе такого сохранения не требует. Снимки подписки удалять после успешной записи. Учесть завершение фонового обновления той же подписки.
6. **Одна операция записи.** Под блокировками контроллера повторно сверять ревизии всех затрагиваемых данных и состав пары, включая происхождение дубликата. При расхождении вернуть новый предпросмотр. Подготовить и проверить весь результат на копиях. Для двух файлов использовать совместимую часть протокола `WriteRulesPair`. Для нескольких файлов предусмотреть восстанавливаемую запись прежнего состояния в защищённом каталоге данных и маркер завершения. При ошибке записи восстановить прежние файлы, в том числе первоначальное отсутствие файла. После прерывания восстановиться до запуска маршрутизации. Опубликовать новое состояние в контроллере только после успешной записи. При ошибке восстановления явно сообщить о ней и не запускать маршрутизацию по частичным данным.

7. **Подсказки и причины подключения.** В `RouteWizard.svelte` обновить существующие пояснения шага серверов и итог, сохранив выбор наследования. В `Home.svelte` использовать строки `st.tunnels` и оставить фактические состояния туннелей. В Go получить структурированные причины по ID вместе с расчётом требуемых серверов (`internal/app/app.go`, `routingLocked`): активный набор правил, разрешение текущего основного, «Всё остальное», раскрытие групп и востребованные локальные прокси. Считать уникальные правила по каждой роли. Для группы показывать участие в группе, явные назначения отличать от наследующих. Список ссылок для удаления охватывает также неактивные профили и имеет другой смысл. Причины отдавать согласованно с состоянием сессии, без побочных действий при опросе статуса. Тестовые туннели уже отфильтрованы в `internal/app/connect.go`.

## Risks / Trade-offs

У неизвестной версии сохранённого профиля могут быть поля, которые клиент не умеет перезаписывать. Предпросмотр должен обозначить такой профиль. Если сохранность ссылок и данных подтвердить нельзя, операция, которая зависит от них, останавливается до записи. Обычная работа с выбранными строками не требует принудительно переводить чужие профили на текущий формат.

## Migration Plan

Проверки проводить на синтетической конфигурации с одним профилем без `rulesets.json` и с двумя профилями. Начальное открытие сохраняет значения и порядок. Для отката неудачного применения используется исходное состояние затронутых файлов. Для отката тестовой версии закрыть тестовый клиент и открыть исходную копию синтетического каталога в соответствующей исходной версии. Рабочая установка владельца в проверке не участвует.

### Ресурсы первой сборки Windows x64

Предварительная оценка на 11.11.2026. Есть Node 22.22.3, npm 10.9.8 и готовый `frontend/dist`. Для изменённого интерфейса его потребуется пересобрать. В кеше npm найдены архивы для 20 из 96 записей клиентского lock-файла (включая необязательные пакеты разных платформ). Команда Go и стандартные кеши модулей и компиляции не найдены. Проект задаёт toolchain Go 1.27.1. Каталоги `bin` и `frontend/node_modules` отсутствуют.

| Статья | Оценка |
| --- | --- |
| Загрузки | Архив Go для Windows amd64 — 78,9 МБ. Клиентские Hysteria, Xray и WinDivert вместе — 40,6 МБ. Известная часть — около 120 МБ. С модулями Go, go-winres и клиентскими npm-пакетами ориентир 200–400 МБ всего. |
| Диск | Свободно около 224 ГиБ на C:. Ориентир первой сборки — 2–4 ГиБ для распаковки Go, зависимостей, кеша компилятора, временных файлов и portable ZIP. |

Перед локальной проверкой 12.11.2026 было свободно около 226 ГиБ. Для тестов получены Go 1.27.1, модули и пакеты интерфейса. Go и его кеши находятся в `.work/`, клиентские пакеты — в `frontend/node_modules`. Эти каталоги можно повторно использовать для portable-сборки.

Оценка относится к клиенту после отделения серверного менеджера. Текущий `scripts/build.ps1` собирает также панель и встраивает её хеш, а `scripts/package.ps1` требует версионный Git-тег. До пробной сборки повторно сверить эти условия и кеши.
